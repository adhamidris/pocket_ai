  Implementation:
  class AgentRunMemoryItem(models.Model):
      # ... existing fields ...

      freshness_tier = models.CharField(
          max_length=10,
          choices=[
              ('hot', 'Hot (0-7 days)'),
              ('warm', 'Warm (7-30 days)'),
              ('cold', 'Cold (30+ days)'),
          ],
          default='hot'
      )

      @property
      def is_stale(self):
          age = timezone.now() - self.created_at
          return age > timedelta(days=7)

      @property
      def staleness_warning(self):
          age_days = (timezone.now() - self.created_at).days
          if age_days < 7:
              return None
          return f"This fact is {age_days} days old and may be outdated"

  Injection Strategy:

              context += f"- {fact.key}: {fact.content}\n"

          context += "\nRecent Facts (may be outdated):\n"
          for fact in warm_facts:
              age = (timezone.now() - fact.created_at).days
              context += f"- {fact.key}: {fact.content} ({age} days old)\n"

      return context

     def get_memory_items_with_freshness(
         run_id: uuid.UUID,
         tenant_config: TenantMemoryConfiguration,
     ) -> dict[str, list[AgentRunMemoryItem]]:
         """
         Get memory items grouped by freshness tier
         """
         items = AgentRunMemoryItem.objects.filter(run_id=run_id)

         hot = []
         warm = []

         for item in items:
             age_days = (timezone.now() - item.created_at).days
             rules = tenant_config.custom_rules.get(item.key, {})
             hot_period = rules.get("hot",
     tenant_config.default_hot_period_days)
             warm_period = rules.get("warm",
     tenant_config.default_warm_period_days)

             if age_days <= hot_period:
                 hot.append(item)
             elif age_days <= warm_period:
                 warm.append(item)
             # Cold items not injected, available via retrieval tool

         return {"hot": hot, "warm": warm}

     ---
     Critical Edge Cases to Handle

     1. Concurrent Tool Executions

     Risk: Multiple tool calls in parallel could interleave content_blocks
     Mitigation: Ensure tool_call_ids are unique per message; add mutex in
     _append_execution_message()

     2. Approval While Compaction is Running

     Risk: If compaction runs during WAITING_APPROVAL, resumed context may
     be stale
     Mitigation:
     - Store pre-compaction checkpoint when entering WAITING_APPROVAL
     - Use existing pending_tool_call metadata to restore exact state
     - Add compaction_checkpoint_id to metadata before compaction

     3. Message ID Drift

     Risk: Race condition between memory update and compaction
     Mitigation: Use expected_last_message_id pattern (already in memory
     update) for compaction

     4. Tool Chain Integrity

     Risk: Reconstructed tool messages may have broken tool_call/response
     chains
     Mitigation: Call _history_requires_tool_anchor() after reconstruction;
     validate all tool_call_ids have responses

     5. Safe Compaction Timing

     Risk: Compaction during active tool loop breaks execution
     Mitigation: Only compact when:
     - Run status is WAITING_APPROVAL, WAITING_EXTERNAL, or COMPLETED
     - No pending tool calls in metadata
     - Mark pending_compaction=True if unsafe, defer to next safe point

     ---
     Key Design Decisions (Validated)

     1. Content Blocks Reconstruction Format

     Decision: Create separate assistant/tool messages (not combined)
     Rationale: Follows existing pattern in build_cached_table_messages()
     (lines 782-857 in prompts.py):
     assistant_message = {"role": "assistant", "content": "", "tool_calls":
     [...]}
     tool_messages = [{"role": "tool", "tool_call_id": id, "content":
     result}]

     2. AgentRunMemoryItem vs structured_memory_v2

     Decision: Keep AgentRunMemoryItem separate from structured_memory_v2
     Rationale:
     - structured_memory_v2 is conversation-scoped (customer-facing chat
     memory)
     - AgentRunMemoryItem is run-scoped (sub-agent operational context)
     - Different lifecycles, different retention requirements

     3. Compaction Infrastructure

     Decision: Extend existing MCP_PROACTIVE_COMPACTION_* patterns
     Rationale: System already has compaction at 90%/85% triggers; we add
     sub-agent specific thresholds (70%/60%)

     4. Retrieval Tool Scope

     Decision: Available to both main chat and sub-agents
     Rationale: Main chat users may reference past tools; sub-agents need it
      for context recovery

     5. Per-Tenant Configuration

     Decision: Use business_profile.metadata["rag_overrides"] pattern
     Rationale: Follows existing FeatureFlagService and business override
