  Investigation Summary

  Architecture Overview

  Your system uses a two-conversation model for sub-agents:

  1. Anchor Conversation - The parent session where the user interacts
  2. Execution Conversation - An isolated conversation created for each agent
  run's work

  This separation is good for keeping the main chat clean, but it's also where
  the session management complexity lives.

  The Flow I Traced

  1. Initial Turn: LLM calls a tool (e.g., email_send_draft), approval is
  required
  2. Approval Created: ConversationToolApproval record with status PENDING
  3. Run Pauses: AgentRun.status → WAITING_APPROVAL, pending_approval_id stored
  in metadata
  4. User Approves: Via portal_agent_run_approval():
    - Approval status → APPROVED
    - A decision message appended to execution conversation: "Approved\nTool: 
  email_send_draft\napproval_id: xxx"
    - Run status → QUEUED
  5. Worker Resumes: Picks up the run, calls orchestrator.stream_turn() with the
   "Approved..." message as user input

  Root Cause Analysis

  I've identified multiple interconnected issues:

  Issue #1: No True "Resume" Semantics

  The system treats the resumed run as a brand new LLM turn rather than
  continuing a paused tool execution. When the worker resumes
  (agent_run_processing.py:1039-1047):

  turn = orchestrator.stream_turn(
      conversation=execution_conversation,
      user_message=turn_user_message,  # "Approved\nTool: email_send_draft..."
      ...
      wait_for_tool_approval=False,  # Don't wait, just return pending
  )

  The LLM sees the transcript and interprets the situation as:
  - "I tried tool X → got an error saying 'pending approval'"
  - "User said 'Approved'"
  - "Let me try tool X again"

  Issue #2: Approval Matching Relies on Exact Input Payload Match

  The code at orchestrator.py:4262-4278 tries to find existing APPROVED
  approvals:

  for candidate in approved_candidates:
      if dict(candidate.input_payload) == redacted_input_dict:  # Strict 
  equality!
          existing_approved = candidate
          break

  If the LLM generates slightly different arguments on retry (different UUID
  format, different key ordering after serialization, extra whitespace, etc.),
  this match fails and a new pending approval is created → infinite loop.

  Issue #3: Decision Message ≠ Tool Result

  When approval is given, a customer message is appended:
  "Approved\nTool: email_send_draft\napproval_id: xxx"

  But this is not a tool result. The LLM's context shows:
  - Tool call with pending_approval error (failure)
  - User message saying "Approved" (acknowledgment)

  The LLM has no indication that the tool should now be considered successful.
  It naturally retries.

  Issue #4: No Tool Call ID Tracking Across Resumes

  Each LLM turn generates new tool_call_ids. The system can't correlate "this
  new tool call is the retry of that previous pending one that was just
  approved."

  class PendingToolExecutor:
      """
      Executes stored pending tool calls after approval.
      Bypasses LLM decision-making for approved operations.
      """

      def execute_pending_tool(
          self,
          run: AgentRun,
          pending_tool: dict,
          execution_conversation: Conversation,
      ) -> ToolExecutionResult:
          """
          1. Validate the pending tool call matches the approval
          2. Execute the tool with stored arguments
          3. Format the result as a proper tool_result message
          4. Inject into the execution conversation
          5. Return result for LLM continuation
          """

          tool_name = pending_tool["tool_name"]
          arguments = pending_tool["arguments"]

          # Execute the actual tool
          if pending_tool.get("connection_id"):
              # MCP remote tool
              result = self._execute_mcp_tool(...)
          elif tool_name.startswith("email_"):
              # Email tool
              result = self._execute_email_tool(...)
          else:
              # Built-in tool
              result = self._execute_builtin_tool(...)

          # Inject result into conversation as tool_result
          self._inject_tool_result(
              conversation=execution_conversation,
