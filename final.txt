  ---
  The MCQ Problem

  Your MCQ isn't bad as a concept, but it has a fundamental design flaw: it's 
  extracting categories from search results that were retrieved BEFORE the 
  system deeply understands what's in the knowledge base.

  Here's what happens today:

  1. User asks "what are Plus segment fees?"
  2. System does ONE search pass (vector + lexical)
  3. Gets back ~6+ hits across multiple documents
  4. Extracts "categories" from those hit metadata (row labels, section
  headings, table titles)
  5. If it looks "broad" (6+ matches, 3+ categories), it stops and asks the user
   to pick

  The problem: those categories come from whatever the first search pass
  happened to surface. They're not a reliable map of what actually exists.
  They're a sample. If the embedding didn't rank a relevant document highly
  enough, that whole category is missing from the MCQ. The user sees 3 options
  and thinks those are ALL the options, but they might be seeing 3 out of 7.

  That's why you feel the categories are "unreliable and insufficient." They
  are. They're a byproduct of one search pass, not a deliberate index of your
  knowledge.

  ---
  The Deeper Question: MCQ vs Full Agentic

  Here's my honest opinion:

  The MCQ makes sense for a DIFFERENT kind of system — a single-shot retrieval 
  system. In a traditional RAG where you get one search, one answer, and that's
  it, asking the user to narrow scope first is smart because you only get one
  chance.

  But you're building an agentic system. The whole point is the LLM can loop. It
   can call search_knowledge multiple times. It can call read_table to drill
  into specific tables. It can progressively build up a comprehensive answer.

  So ask yourself: what does the MCQ actually save?

  - If the user picks "Cheques fees" → the agent searches for cheques fees →
  gives answer
  - If there's no MCQ → the agent searches broadly → finds cheques, accounts,
  teller, loans fees → synthesizes a comprehensive answer that covers everything

  In the second case, the user gets MORE value with LESS friction. They didn't
  have to make a choice they might not even be qualified to make (a new bank
  customer doesn't know your product categories).

  The MCQ is solving a retrieval limitation, not a user need. You added it
  because the system couldn't handle broad queries well in a single pass. But
  the right fix is making the system handle broad queries better — which is
  exactly what agentic looping does.

  ---
  When an MCQ DOES Make Sense

  I'm not saying never prompt the user. There are legitimate cases:

  1. True ambiguity: "What's the fee?" — fee for WHAT? The system genuinely
  can't know. But even here, the agent could say in prose: "I found fees related
   to cheques, accounts, and cards. Which area are you asking about?" — that's a
   natural conversational clarification, not a rigid MCQ widget.
  2. Action confirmation: Before executing something irreversible. Not relevant
  for read-only queries.
  3. Preference, not information: "Do you want this in Arabic or English?" — the
   knowledge base can't answer this.

  For your core use case — "find me all fees for segment X" — the MCQ is
  friction. The agent should just go find them all.

  ---

  User: "What are the fees for Plus segment?"

  Agent loop 1: Search broadly for "Plus segment fees" → gets hits from

⏺ You're right to worry. The flag being off is not sufficient for a clean
  system. Here's the honest picture:

  What the flag does protect you from:

  - The MCQ UI widget won't render (server won't send it)
  - MCQ diagnostic payloads won't be built
  - Scope selection turn-lock won't activate

  What STILL runs every single query even with MCQ off:

  1. Category extraction on every search (the biggest waste):
  _build_scope_summary_from_candidates() in ai_orchestrator.py runs
  unconditionally. Every time a user searches, it iterates through ALL hits,
  extracts row_labels, table_titles, section_headings, parses content for
  key-value pairs, counts categories, and builds a scope summary. All of this is
   thrown away when MCQ is off.

  2. Broad scope detection still triggers needs_clarification:
  Even with MCQ off, when the RAG layer detects "broad scope" (6+ matches, 3+
  categories), it still returns status=needs_clarification with
  clarification_ui_mode=text. The LLM then gets told to write a prose
  clarification instead of MCQ — which also interrupts the agentic flow. This is
   the text-mode fallback that your previous agents built as "Plan B."

  3. Sanitization functions still run on every clarification path, doing dict
  key removal operations for no reason.

  4. Dead functions sitting in the codebase (~250+ lines across tools.py):
  bucket ID logic, MCQ diagnostics builders, category ref mapping — all
  unreachable but adding confusion for any agent or human reading the code.

  What's safe and should stay:

  The table scope metadata in ingestion (scope columns, inferred_scope_columns,
  applicability segments) — this is table structure data that helps retrieval
  quality. It has nothing to do with MCQ.

  ---
  My recommendation:

  Yes, you should clean this up. But it's not urgent enough to block your
  testing. I'd suggest:

  1. Immediate (do now): Also disable the text-mode clarification fallback,
  because that ALSO interrupts the agentic flow. The broad-scope detection
  returning needs_clarification with mode=text is just MCQ-lite — the LLM still
  stops to ask instead of investigating.
  2. Soon (next session): Remove the dead MCQ code and the category extraction
  overhead. It's ~300 lines of dead code across tools.py and unnecessary
  computation in ai_orchestrator.py on every search.

  Want me to do the immediate fix now (disabling the text-mode clarification
  fallback so the agent never gets interrupted by scope detection), and leave
  the dead code cleanup for a separate session?
