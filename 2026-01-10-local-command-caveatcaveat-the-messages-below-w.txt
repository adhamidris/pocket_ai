  The Real Issue

  Think of it like this:
  What Should Be Cached: "This PDF has a table about credit cards" (the
    reference)
  What's Actually Cached: "Here are the rows about issuance fees" (query-specific
     sample)
  When you ask "what are the issuance fees?", the system:
  1. Finds the table
  2. Extracts only the rows relevant to "issuance fees"
  3. Caches that specific extraction

  When you then ask "what are ALL the fees?", the system:
  1. Sees "oh I already have this table cached"
  2. Reuses the issuance-fees-only extraction
  3. Misses all the other fee columns because they weren't in the original sample

  The Smart Fix

  Cache the table REFERENCE, but re-sample the ROWS for each new question.

  Turn 1: "issuance fees?"
    → Cache: "Table X from Credit Cards PDF is relevant"
    → Sample: rows with issuance fee data
    → Result: ✓ All 10 cards

  Turn 2: "all fees?"
    → Cache HIT: "Table X is still relevant" (good, saves search time!)
    → Re-sample: rows with ALL fee columns (based on new query)
    → Result: ✓ All 10 cards with all fees

  This gives you:
  - Speed: No need to re-search the entire knowledge base
  - Accuracy: Fresh row extraction per question

  Current Broken Flow

  Turn 1: "issuance fees?"
    → Sample: issuance fee rows only
    → Cache: the actual sampled content (locked in)

  Turn 2: "all fees?"
    → Cache HIT: reuses issuance-fee-only content (stale!)
    → No re-sampling happens
    → Result: ✗ Missing data

● Honest answer: Option B is a pragmatic fix, but not the ideal long-term architecture.

  Let me explain what modern platforms actually do:

  How Modern RAG Systems Handle Tables

  The best systems separate three concerns:
  Stage: 1. Identification
  What It Does: "Which tables are relevant to this conversation?"
  Should Be Cached?: ✓ Yes
  ────────────────────────────────────────
  Stage: 2. Extraction
  What It Does: "Which rows/columns answer THIS specific question?"
  Should Be Cached?: ✗ No - query-time
  ────────────────────────────────────────
  Stage: 3. Formatting
  What It Does: "How do I present this data to the LLM?"
  Should Be Cached?: ✗ No - query-time
  Your current system merges all three into one cached blob - that's the architectural flaw.

  What The Proper Fix Looks Like

  During Ingestion:
  - Extract tables into a structured format (rows, columns, cells as queryable data)
  - Store this separately from the text chunks
  - Think of it like a mini-database per table

  During Retrieval:
  - Identify relevant tables (cacheable)
  - Query the structured table data based on the current question (not cached)
  - Format for the LLM (not cached)

  Ingestion:
    PDF → Table detected → Store as structured JSON:
    {
      "table_id": "credit_cards_fees",
      "columns": ["Card Type", "Issuance Fee", "Interest Rate", ...],
      "rows": [
        {"Card Type": "White", "Issuance Fee": "500", ...},
        {"Card Type": "Classic", "Issuance Fee": "250", ...},
        ...
      ]
    }

  Query Time:
    "What are all the fees?"
      → Identify: table "credit_cards_fees" is relevant
      → Extract: SELECT all fee-related columns
      → Format: Present complete fee data to LLM

  Industry Examples

  - Vectara, Pinecone: Hybrid search with metadata filtering - tables stored structurally
  - LlamaIndex: Has dedicated TableIndex that queries tables like a database
  - OpenAI's Assistants API: Uses code interpreter to query tabular data programmatically
  - Enterprise platforms (Glean, Coveo): Separate structured data pipelines from unstructured text

  My Recommendation

  Short-term (Option B): Re-sample cached table chunks with the current query. This fixes your immediate problem with minimal code change.

  Long-term (Proper Architecture):

  1. During ingestion, store tables as structured JSON (you may already have this in structured_tables)
  2. Cache only the table reference (table_id, upload_id, column names)
  3. At query time, query the structured data based on the current question
  4. Never cache the extracted row content

  def _refresh_table_sample(
      self,
      cached_entry: dict[str, object],
      query: str,
  ) -> dict[str, object]:
      """
      For cached table chunks, re-sample rows based on the current query.
      This ensures follow-up questions get query-optimized table data.
      """
      # Only refresh table chunks
      if not cached_entry.get("is_table_chunk"):
          return cached_entry

      chunk_id = cached_entry.get("chunk_id")
      if not chunk_id:
          return cached_entry

      # Fetch the chunk from DB
      try:
          from apps.accounts.models import KnowledgeUploadChunk
          chunk = KnowledgeUploadChunk.objects.filter(id=chunk_id).first()
          if not chunk:
              return cached_entry
      except Exception:
          return cached_entry

      # Re-sample with current query
      fresh_tables = self._table_row_sample(
          chunk,
          max_columns=6,
          max_rows=3,  # Allow more rows for comprehensive queries
          query=query,
      )

      # Update the cached entry with fresh data
      refreshed = dict(cached_entry)
      refreshed["structuredTables"] = list(fresh_tables)
      refreshed["needs_table_refresh"] = False
      return refreshed

  # BEFORE:
