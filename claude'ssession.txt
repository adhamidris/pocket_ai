⏺ Now I have a thorough picture of your retrieval pipeline. Here's my analysis:

  Your Current State

  Currently in your codebase:

  - Deduplication is identity-based only (_anchor_key in tools.py:3979-4015) —
  it prevents the exact same chunk from appearing twice, but does NOT group
  different chunks from the same document
  - Table row expansion (ai_orchestrator.py:7347-7504) expands parent table
  chunks into individual rows, which can flood slots with rows from one table
  - RRF fusion (ai_orchestrator.py:5816-5883) merges by snippet ID, not by
  document — so a document with 3 matching chunks gets 3 independent RRF scores
  and 3 slots
  - The hard cap is MCP_PROMPT_MAX_SNIPPETS (default 4) for LLM-visible results,
   and MCP_SEARCH_KNOWLEDGE_DEFAULT_LIMIT (default 10) for the search return

  Your Intuition Is Correct — and It's a Well-Known Pattern

  This is absolutely a recognized concern in modern RAG. What you're describing
  has a few established names:

  1. Document-level grouping / collapsing — Elasticsearch calls this "field
  collapsing", Vespa calls it "grouping". The idea is identical to yours: group
  hits by a parent key (document/upload_id), present the group as one slot, and
  include the individual chunks within it.
  2. Parent Document Retrieval — a LangChain/LlamaIndex pattern where you
  retrieve by chunk but return the parent document or a merged window. Same core
   idea.
  3. Maximal Marginal Relevance (MMR) — a softer version: instead of hard
  grouping, you penalize results that are semantically similar to
  already-selected results, which naturally diversifies across documents.

  Why It Matters for Your System

  Looking at your example output, CIB-Remittance-EN.pdf takes 3 of 10 slots
  (chunks 4, 5, 6). If you group them:
  Before (current): Slot 1: Tariff — Cheques-EN – Table 1
  After (grouped): Slot 1: Tariff — Cheques-EN – Table 1
  ────────────────────────────────────────
  Before (current): Slot 2: CIB-Remittance-EN.pdf – chunk 4
  After (grouped): Slot 2: CIB-Remittance-EN.pdf – chunks 4, 5, 6
  ────────────────────────────────────────
  Before (current): Slot 3: CIB-Account-EN.pdf – chunk 3
  After (grouped): Slot 3: CIB-Account-EN.pdf – chunk 3
  ────────────────────────────────────────
  Before (current): Slot 4: Mortgage.pdf – chunk 2
  After (grouped): Slot 4: Mortgage.pdf – chunk 2
  ────────────────────────────────────────
  Before (current): Slot 5: CIB-Remittance-EN.pdf – chunk 5
  After (grouped): Slot 5: CIB-Customer Service-EN.pdf – chunk 2
  ────────────────────────────────────────
  Before (current): Slot 6: CIB-Customer Service-EN.pdf – chunk 2
  After (grouped): Slot 6: alternative-channelsen.pdf – chunk 3
  ────────────────────────────────────────
  Before (current): Slot 7: alternative-channelsen.pdf – chunk 3
  After (grouped): Slot 7: (new document that was previously slot 11+)
  ────────────────────────────────────────
  Before (current): Slot 8: CIB-Remittance-EN.pdf – chunk 6
  After (grouped): Slot 8: (new document)
  You go from 6 unique documents in 8 slots to 6+ unique documents in 8 slots 
  with 2 freed slots for new sources. The LLM still gets to read all 3
  Remittance chunks (same content), but the result diversity improves
  significantly.

  Nuances to Consider

  1. Don't lose the relevance signal. When 3 chunks from one document rank in
  the top 10, that's actually a strong signal that this document is highly
  relevant. Your grouping should preserve this — put the grouped result at the
  rank of its highest-ranking chunk, not at the average or lowest.

  2. Token budget matters more than slot count. Grouping 3 chunks into 1 slot
  doesn't reduce the tokens the LLM needs to read — it's the same content. The
  real win is diversity: the freed slots let you surface documents that would
  have been pushed to slot 11+ (invisible). But watch out for grouped results
  becoming massive — you might want a per-group char cap.

  3. The agentic two-phase pattern helps here. Your system already has a
  search_knowledge → read_document two-phase flow in agentic mode. In this
  model, consolidation is even more natural: the search returns lightweight refs
   grouped by document, and the LLM decides which groups to read_document on.
  The grouping happens at the ref level (cheap), not at the content level.

  4. Table rows are a special case. Your table row expansion already creates the
   exact problem you're describing — one table can spawn 20 row chunks
  (RAG_TABLE_ROW_EXPANSION_LIMIT). Grouping by table_id is the highest-impact
  consolidation you can do, and it sounds like you've already started on this.

  My Recommendation

  Your approach is sound and aligns with industry practice. The implementation
  path I'd suggest:

  - Group by upload_id (document level) as the primary key, with table_id as a
  sub-group key for table chunks within the same document
  - Rank the group by its best chunk's score (highest RRF or confidence score in
   the group)
  - In the agentic ref format, represent it as one ref with a chunks: 
  [{chunk_index: 4}, {chunk_index: 5}, {chunk_index: 6}] array and a combined
  char_estimate
  - Cap per-group content to something like 2x-3x the suggested_max_chars of a
  single chunk, so one document can't monopolize the token budget
  - Keep the ungrouped results in the prefetch cache
  (SEARCH_PREFETCH_ABSOLUTE_CAP = 200) so pagination still works at the chunk
  level if the LLM wants to drill deeper

  This is not an exotic idea — it's a gap that most RAG systems eventually close
   as they mature. You're thinking about it the right way.

⏺ Codex raises four criticisms. Let me go through each honestly.

  1. "Full doc scan from chunk 0..max burns budget on big PDFs"

  Codex is right, this is the most legitimate concern. If
  "CIB-Remittance-EN.pdf" has 150 chunks and the matched ones are chunks 40, 42,
   45 — my plan reads from chunk 0, burning the budget on 40 irrelevant chunks
  before reaching the relevant ones. The budget cap prevents reading everything,
   but you'd still waste most of it on the wrong region.

  The fix Codex suggests (read from min(chunk_indices)..max(chunk_indices) ± 
  context) is better. The real problem is: how does the read handler know which 
  chunk indices were in the group?

  The read input is normalized to just {id, cursor} at line 6768 — the
  coverage_hint.chunk_indices from the search response doesn't survive into the
  read handler. So the read handler can't know the window bounds without
  re-deriving them.

  The cleanest solution: during search shaping, cache the group metadata 
  server-side (e.g., in the conversation turn's cache, keyed by
  text_group:{upload_id}). The read handler then looks it up — no metadata
  passthrough needed, no contract change.

  2. "Pre-queries duplicate what _resolve_target already does"

  Partially valid, somewhat overstated. The pre-query identifies upload-level
  refs upfront so the "covered" pattern works predictably. _resolve_target does
  resolve IDs, but it runs inside the loop — you'd need the upfront knowledge to
   handle ordering edge cases (what if an individual chunk ref appears before
  the document anchor in the read request?).

  That said, the pre-query can be eliminated if we just track state in-loop and
  handle the ordering naturally: process the document anchor, add to
  expanded_upload_reads_seen, then when subsequent individual chunks from the
  same upload_id are encountered, mark them "covered." If an individual chunk
  appears before the anchor in the read list, it just reads normally — no harm
  done, slightly less optimal but correct.

  Verdict: the pre-query is unnecessary complexity. In-loop tracking is simpler 
  and sufficient.

  3. "Covered checks before access enforcement is risky"

  Codex is right, easy fix. The "covered" check should go after _enforce_access
  (after line 7581), not before it. The document anchor that "covers" the chunk
  has the same upload_id and thus the same access rules, so in practice nothing
  would break — but skipping access checks is bad practice regardless. Moving it
   two lines down fixes this.

  4. "Manifest not usable — read input normalizes to {id, cursor}"

  fix naively. The search response carries coverage_hint.chunk_indices = [40, 
  42, 45], but the read handler never sees it because the input normalization at
   line 6768 strips everything except id and cursor.

  This is why I'd use server-side caching rather than metadata passthrough: the
  search handler writes the group manifest to a turn-scoped cache, the read
  handler reads it. No contract changes, no normalization issues.

  Consolidation is working but has limited impact on this query. In all 3
  searches, each document already appeared at most once — there wasn't a case of

  search slot.
